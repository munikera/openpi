Why Vision-Language-Action Models?

The Problem — Generalization

🤖 Traditional Robot Policies

Learned policies can extrapolate to new initial conditions (object position, lighting) but fail to generalize to:

  • Scene distractors or novel objects
  • Unseen task instructions
  • Robots or environments not in training
📦 The Data Gap

Root cause: robot manipulation datasets are tiny compared to Internet-scale data.

100K–1M
largest robot datasets
Billions
internet-scale vision/text

This imbalance suggests an opportunity: use existing foundation models as a core building block.

🚧 Why Closed Models Aren't Enough

Even capable VLAs (RT-2, etc.) have two blockers for widespread adoption:

  • Closed weights — no visibility into architecture, training data, or procedures
  • No deployment guidance for new robots, environments, or commodity hardware

The Solution — Borrow Internet-Scale Priors

💡 Core Idea: VLA = VLM + Action Head

Take a Vision-Language Model already trained on billions of images and text — then fine-tune it to output robot actions instead of words.

HOW THE PIECES CONNECT

SigLIP and the LLM are pretrained on internet data and bring rich visual + semantic priors. Only the action head (and light fine-tuning) is trained on robot data.

Result: VLAs like RT-2, OpenVLA, and π0.5 demonstrate impressive generalization to novel objects and tasks — because SigLIP and the LLM already "understand" the visual world from internet-scale pretraining.

Why so few patches?

Both models use standard PyTorch ops — nn.Linear, attention, layer norm. With torch 2.10.0+xpu these dispatch natively to Intel Level Zero. The main work was removing hardcoded .cuda() calls and switching the package index.

⚠️ Subprocess Architecture (π0.5 + LIBERO)

Loading π0.5 onto XPU installs process-wide Level-Zero memory hooks that conflict with MuJoCo's osmesa allocator → segfault. Fix: LIBERO runs in a clean worker subprocess that never imports torch. IPC via pickle over stdin/stdout.

LIBERO Benchmark — MuJoCo Simulation

What is LIBERO?

A standardized benchmark for robot manipulation built on MuJoCo physics simulation. The robot arm operates in a tabletop scene with camera observations and receives natural language task instructions. Tests whether a policy can generalize across different conditions.

OpenVINO Optimization — One Compiled Graph

The core idea

Instead of dispatching thousands of kernels at runtime, compile the entire model into a pre-planned GPU execution graph once. At inference time, a single API call triggers the whole thing — prefix pass + all N denoising steps.

Export pipeline

1
PyTorch → ONNX  torch.onnx.export
The full model — including the N-step denoising loop unrolled — is traced into a single static ONNX graph. KV cache stays internal. ~2–5 GB file.
2
ONNX → OV IR  ov.convert_model
OpenVINO's model optimizer converts ONNX ops to its internal representation optimized for Arc GPU via the oneDNN backend. Produces model.xml + model.bin.
3
Compile + Infer  Arc GPU plugin
core.compile_model() — runs once (~30–60 s), plans all GPU work. Then infer_req.infer(inputs) — one call, near-zero CPU overhead.

What changes at runtime

PyTorch XPU  117 ms
GPU 79 ms
CPU 38 ms — 4,793 launches
OpenVINO FP32  ~88 ms
GPU + dispatch ~88 ms — 1 infer() call

Breaking 100 ms — 5-Step Denoising

Flow Matching is Robust to Fewer Steps

Unlike diffusion models, flow-matching trajectories are nearly straight lines in data space. 5 steps ≈ same success rate as 10 steps on all LIBERO benchmarks (confirmed by BLURR paper and Physical Intelligence ablations), with ~1.6× speedup.
