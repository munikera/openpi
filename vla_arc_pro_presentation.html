Action Representation — The Hard Problem

How should a VLA encode robot actions? The answer shapes inference speed, precision, and real-time viability.

Approach 1

Discrete Bins

RT-1 · RT-2 · OpenVLA

Each action dimension (joint angle, gripper) is bucketed into 256 discrete bins and treated as a token — same as a word. The VLM predicts one action token at a time.

Action chunk encoded as tokens:
[128, 201, 43, 187, 92, 255, 14]
7 joints → 7 tokens → 7 autoregressive steps
✓ Simple — reuses standard LLM training (cross-entropy)
✓ Works well for coarse manipulation tasks
✗ Loses precision — binning fails for dexterous tasks
✗ Slow autoregressive inference — hard to hit <100 ms

Approach 2

Continuous Action Head

π0 · π0.5

The VLM backbone handles vision and language reasoning. A separate flow-matching action expert takes the VLM's output and iteratively denoises a continuous action trajectory from random noise.

Flow matching: noise → action
N(0,1) → step 1 → step 2 → … → [0.12, -0.34, 0.87…]
Continuous floats — full precision, no binning loss
✓ Full precision — no binning loss, handles dexterous tasks
✓ Flow matching is fast — as few as 5 steps sufficient
✓ Knowledge insulation: VLM backbone kept frozen → better generalization
⚠ Loop must be unrolled at export time for OpenVINO

VLA Models We Evaluated

Two models were selected based on stakeholder input: OpenVLA (ECG team, embedded target) and π0.5 (our primary B70 target, requested by Mark Iskra / Physical Intelligence contact).

OpenVLA  7B params

ECG Team Focus
  • Backbone: Prismatic VLM — SigLIP visual encoder + Llama-2 7B
  • Training: Fine-tuned on Open-X-Embodiment (diverse robot data)
  • Inference: Single autoregressive forward pass → discrete action tokens
  • Target: PTL / LNL iGPU + NPU for embedded robotics (ECG team)

π0.5 (pi0.5)  3B params

Our Focus
  • Backbone: PaliGemma — SigLIP + Gemma 2B language model
  • Action head: Flow-matching expert denoises over N steps
  • Inference: Prefix pass (fills KV cache) + N denoising steps per call
  • Target: Arc Pro B70 workstation — 10+ Hz closed-loop control

Runtime Architecture — Why a Worker Subprocess?

Loading the 3B model onto XPU installs process-wide Level-Zero memory hooks that conflict with MuJoCo's osmesa CPU allocator → segfault. Fix: LIBERO runs in a clean subprocess that never imports torch.

⚠️ The Problem: CPU Dispatch Gap

NVIDIA benefits from mature CUDA Graph support — near-zero CPU overhead. XPU dispatch overhead is ~38 ms vs ~7 ms on NVIDIA. This is the gap OpenVINO closes by compiling the full graph ahead of time.

Key insight: B70 GPU compute is already competitive with RTX PRO 4000 (79.8 ms vs 76.3 ms). The entire performance gap is software overhead, not hardware capability.

OpenVINO Optimization — Export Pipeline

Strategy: Unroll + Monolithic Graph

The denoising loop runs N times per call. Standard export would need N Python calls → keeping CPU overhead. Instead, the N-step loop is unrolled at ONNX export time. KV cache stays internal. One infer() call covers prefix + all N denoising steps.

1
Cast bf16 → fp32  PyTorch
All model params/buffers cast before tracing. ONNX opset 17 doesn't natively support bfloat16.
2
torch.onnx.export  opset 17, TorchScript
Legacy exporter with ONNX_ATEN_FALLBACK. Loop unrolled into static graph. ~2–5 GB file. Requires ulimit -n 65536.
3
ov.convert_model → OV IR FP32  OpenVINO 2025.4
ov.save_model(compress_to_fp16=False) → model.xml + model.bin.
4
Compile on Arc Pro B70 GPU Plugin
GPU_ENABLE_SDPA_OPTIMIZATION: YES. First compile ~30–60 s. One infer_req.infer() call = full inference.

Breaking 100 ms — 5-Step Denoising

Flow Matching is Robust to Fewer Steps

Unlike diffusion models, flow-matching trajectories are nearly straight lines in data space. 5 steps ≈ same success rate as 10 steps on all LIBERO benchmarks (confirmed by BLURR paper and Physical Intelligence ablations), with ~1.6× speedup.
