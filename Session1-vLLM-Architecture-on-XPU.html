vLLM Internal Architecture

XPU is an in-tree device in vLLM — supported directly in the upstream repository, not a plugin or fork. It shares the same worker, model runner, model definitions, and op interfaces as CUDA and AMD. The key difference across platforms is the kernel provider layer.

Execution Modes on XPU

Three execution modes — CUDA uses Compile + CUDAGraph by default. XPU is working towards Compile as the default path.

Mode How It Works Pros Cons XPU Status
Eager Ops dispatched one-by-one at runtime Always works, easy to debug Launch overhead per op, no fusion Default, Production
Compile torch.compile traces & fuses ops via TorchInductor Automatic op fusion, reduced overhead, Inductor handles new op patterns seamlessly Startup compilation warmup Towards Default
XPU Graph Capture and replay execution graphs (full graph or piecewise with compile) Lowest latency, minimal launch overhead Static shapes only, higher memory Experimental

Direction: Move XPU to Compile by default, matching CUDA parity. Under compile, prefer torch-native ops so Inductor can fuse and optimize them automatically. Also enabling vLLM built-in fusion passes (e.g., Async TP, quantization fusions) on XPU — these are general LLM workload patterns already defined in vLLM.

XPU Graph note: Experimental in vLLM. Currently supports single card only with piecewise compilation. Full graph capture and multi-card support expected in DLE 2026. Performance will depend on L0 native graph maturity.

Model Parallelism & Communication

StrategyWhat It DoesComm Ops
Tensor Parallel (TP) Splits weight tensors across GPUs AllReduce
Pipeline Parallel (PP) Splits model layers across GPUs Send / Recv
Expert Parallel (EP) Distributes MoE experts across GPUs All-to-All (Dispatch / Combine)
Data Parallel (DP) Replicates model, splits requests. Common for MLA workloads — no KV cache duplication. Typically combined as DP×TP with EP to increase concurrency —

TP is the most common — used in nearly all multi-GPU serving deployments (TP4, TP8). EP is critical for large MoE models; DeepEP-equivalent support is planned.

When to use which

  • FLASH_ATTN — Default backend, well optimized on XPU with SYCLTLA
  • TRITON_ATTN / MLA — Broader coverage (e.g., head_size=512, MLA)
  • GDN_ATTN — GatedDeltaNet (Qwen3.5, Qwen Next)
  • XPU_MLA_SPARSE — Sparse MLA (DeepSeek V3.2, GLM-5)

FLASH_ATTN is the default attention backend on XPU, aligned with FlashAttention v2/v3 API. Well optimized with SYCLTLA-based chunked prefill and decode-only kernels for high-performance execution.

Inside Model Runner (V1 Engine)

Token-centric Unified Step

In V1, there is no explicit prefill/decode phase. Tokens are the first citizen — each step processes a batch of tokens from different requests, mixing new-request tokens and ongoing-decode tokens together.

Chunked Prefill

Long prompts are broken into chunks and interleaved with decode tokens in the same batch. This keeps decode latency stable while processing new requests.

Metadata Drives Kernels

The runner passes per-request metadata — num_computed_tokens, num_scheduled_tokens — so kernels know each token’s context (new vs. cached, position in sequence) without separate code paths.

Get Started

Docker (Recommended)

# Build from source
$ git clone https://github.com/vllm-project/vllm
$ cd vllm
$ docker build -f docker/Dockerfile.xpu \
    -t vllm-xpu .

# Run serving
$ docker run --rm -it \
    --device /dev/dri \
    -v ~/.cache/huggingface:/root/.cache/huggingface \
    -p 8000:8000 \
    vllm-xpu \
    --model Qwen/Qwen2.5-7B-Instruct

# Test with curl
$ curl http://localhost:8000/v1/completions \
    -H "Content-Type: application/json" \
    -d '{"model": "Qwen/Qwen2.5-7B-Instruct",
        "prompt": "What is vLLM?",
        "max_tokens": 128}'
